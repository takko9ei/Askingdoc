## 1. 为什么用 RAG 而不是长上下文

**问题**：现在的LLM context window已经能装下几十万token，576页的说明书全文大概
二三十万字符，理论上能整本塞进prompt，为什么还要做检索这一套？

**方案**：用RAG——先检索出跟问题相关的几个片段，再把这几个片段喂给LLM生成答案，
而不是每次都把整本书当上下文传进去。

**代价权衡**：
- 长上下文的代价是**成本和延迟**——如果每次提问都要传二三十万token，按量计费的API
  成本会很高，而且首token延迟会因为要处理这么长的输入而明显变长，对一个"用户问一句、
  马上要答案"的问答场景不划算。
- 长上下文还有"lost in the middle"问题——已有研究表明LLM对超长上下文中间部分的信息
  召回能力会下降，不是"给的信息越多回答越准"，而检索能保证喂给模型的是精选的、高相关的
  内容，信噪比更高。
- RAG的代价是需要额外的工程量——建索引、维护检索链路、做消融实验验证效果。这个项目
  用四组消融数据（Recall@5从baseline的90%到hybrid的100%）证明了检索模块确实在起作用，
  不是凭空加复杂度。
- **RAG还有一个长上下文给不了的能力：精确到页码的引用溯源**——这是企业文档问答场景的
  硬需求（"这个答案的依据在第几页"），长上下文方案没有天然的机制去标注"这句话来自原文
  哪个具体位置"，而RAG的检索结果本身就带着页码。

## 2. 为什么需要双路索引（向量和BM25各自的盲区）

**问题**：只用向量检索够不够？

**方案**：向量（语义）+ BM25（关键词）双路并行建索引，检索时融合两边结果。

**代价权衡**：需要维护两套索引（存储空间翻倍，但实测205条文档BM25索引构建只要几秒，
代价很小），而且两边的查询分词必须完全一致（`tokenize`只有一份实现，见项目【铁律】），
否则BM25会静默失效。

**两条真实盲区案例，互相印证**：
- **向量检索的盲区**：项目里第112-113页是一个多列排布的超链接跳转目录，被PyMuPDF解析
  成了一整块乱麻文本。问"识别优先级设置是在设置什么"，向量检索**完全找不到**这个页面
  （语义已经被打碎），但"优先级设置"这四个字**字面上**就在那团乱文本里——BM25直接把它
  排到第1名，融合后进了top-3。加了BM25之后，这道题的Recall@5从"完全找不到"变成"命中"，
  是整个消融实验里效果最直接的一次改进。
- **BM25的盲区**：反过来，如果用户问"连拍能拍多少张不卡"这种口语化表达，文档原文写的
  可能是"缓冲区容量约23张"，字面上"不卡"和"缓冲区容量"完全对不上，BM25在这种场景下
  会失效，得靠向量检索的语义理解才能命中。

两条路径的失败模式不同，融合能覆盖住任何一条单独存在的盲区。

## 3. 为什么用 RRF 而不是加权分数融合

**问题**：两路检索结果各自带一个分数，为什么不直接按权重加起来？

**方案**：RRF（Reciprocal Rank Fusion）—— `score(d) = Σ 1/(k + rank_r(d))`，
用文档在每一路里的**排名**而不是**原始分数**做融合，`k` 取60（社区常见经验值）。

**为什么不能用分数加权**：项目实测过两路分数的真实量纲——向量检索的分数（转换成余弦
相似度后）在0~1之间，比如`0.572`；BM25的原始分数无上界，取决于词的稀有程度和语料
规模，实测同一批候选里从`0.5`到`22.4`都有。这两组数字**不是一个尺度**，直接加权
求和没有意义（BM25分数一高就会完全压过向量分数）。想解决就得先归一化，但归一化本身
很脆弱——min-max归一化的"最大值"会随每次查询的候选集变化而变化，同一份候选质量在
不同查询下可能被归一化成不同的权重。

**RRF怎么绕开这个问题**：不管底层分数是`0.572`还是`22.4`，"排第1"这件事的含义在
两路里是完全对等的，可以直接相加。

**k的作用**：`k`是个缓冲垫，压低排名差异对最终分数的影响幅度。`k`越小，排名第1和
第2的分数差距越悬殊（更信任"谁的第1名更靠谱"）；`k`越大，各排名的分数越接近
（更看重"两路是否都覆盖到了这个文档"，即"共识"效应更明显）。`k=60`是拿来即用的
经验值，不是针对这个项目调过的最优解。

**代价**：RRF丢失了原始分数的**绝对差距**信息——两个候选如果原始分数差10倍但排名
相邻，RRF会认为它们"差不多相关"，这在某些场景下可能不够精细。项目实测中也观察到
一个真实代价：向量检索原本排第1（近乎完美命中）的候选，融合BM25后如果BM25对同一
查询的排序不认同，会被拉低到第2、第3名（"清理CMOS"这道题就是活案例）——RRF换来了
"两路都找不到时互相补救"的能力，但对"某一路已经答得很准"的情况，反而可能是一种干扰。

## 4. 为什么需要 Cross-Encoder 重排

**问题**：融合后的候选顺序已经不错了，为什么还要再做一次重排？

**方案**：用Cross-Encoder（`BAAI/bge-reranker-v2-m3`）对候选重新打分排序。

**Bi-Encoder vs Cross-Encoder**：向量检索用的Bi-Encoder把query和文档**分别独立**
编码成向量，两者从始至终没有"交互"，相似度全靠事后比较两个向量的夹角——这样做的
好处是文档向量可以提前算好存起来，查询时只需要现算query向量再做最近邻搜索，能扫
全库。Cross-Encoder把query和文档**拼在一起**塞进同一个模型，每一层都能让两段文本
互相"看见"对方，能捕捉更细粒度的语义关系，精度更高，但代价是**分数无法提前计算**
（依赖query和候选文档两者共同决定），只能在候选池已经缩小之后再跑。

**两阶段架构的普遍性**：这不是本项目独有的设计，几乎所有真实搜索/推荐/广告排序系统
都是这个思路——先用便宜的方法（向量/BM25）从海量数据里粗筛出一小撮候选，再用贵但准
的方法只在这一小撮里精排。本质是把"茫茫大海里快速捞出候选"和"候选里精细排序"这两种
不同性质的计算分开处理，而不是硬指望一个模型两头都好。

**代价（含一次真实的负面案例）**：延迟是最直接的代价——实测20个候选重排一次约2.3秒，
候选数一旦失控（曾经历过因为一个bug涨到38个候选，耗时随之涨到4.3秒），CLI交互体验
会明显变差。**更值得讲的代价是：重排不是无脑的全面提升**——本项目dev消融数据里，
`hybrid`→`rerank`，Recall@5从100%反而掉回90%，MRR只涨了0.004（0.637→0.641）。
逐题排查发现：重排确实修好了"清理CMOS"（候选池里有个稀释了话题的假阳性块排第1，
重排后被正确的答案页替换到第1名），但同时搞砸了"如何使用触摸功能图标进行拍摄"——
候选池里一堆内容都在讲"触摸功能图标"这个大主题（隐藏图标/播放画面图标/拍摄画面
图标……），Cross-Encoder把这些同主题内容全判成高相关（分数普遍0.78~0.97），反而
没能精细区分出"具体怎么拍摄"这个更窄的意图，把真正的答案挤出了top-10。**这个案例
说明Cross-Encoder在"候选质量差异大"的场景下效果显著，在"候选主题高度同质、只是
场景细分不同"的场景下，反而可能因为判别力不够精细而帮倒忙**——这是个比"数字全线
上涨"更有分析深度的真实发现。

## 5. 为什么 small-to-big（检索精度与生成完整性的矛盾）

**问题**：检索和生成对"片段大小"的要求是相反的，怎么解决？

**方案**（STEP5，尚未实现）：切两级——child（~300 token，供检索用，语义聚焦）
和parent（~1500 token，供生成用，上下文完整），child记住自己的`parent_id`。
只有child进向量库参与检索，命中后换回它所属的parent喂给LLM。

**矛盾的具体表现**：块越大，向量方向越模糊，命中精度越差——一个塞了8-9个不相关
话题的大块（本项目实测中`c_0001`/`c_0002`这类"目录式"child就是真实案例，本来是
手册开篇的功能速览，被切分算法拼进了同一个child，问任何一个子话题，这个块的向量
"哪个都不太像"）。但块太小，生成时又会丢失关键上下文——比如一句"约23张"如果没有
前面"连拍模式下"这个限定条件，LLM要么瞎猜要么答不完整。

**预期代价**：需要维护两级数据结构（parent/child各自独立存储，靠`parent_id`关联），
检索命中多个child对应同一个parent时需要去重（分数取最高），去重后数量不足`final_top_k`
时要从剩余候选里补足以保持返回数量稳定。上下文变长对生成也有双面影响——完整性提升的
同时，也可能引入更多无关内容稀释LLM的注意力，这个权衡需要STEP5实现后用真实数据验证。

## 6. 为什么 page_no 必须在解析阶段保存

**问题**：页码信息为什么不能等到后面环节需要引用的时候再补？

**方案**：STEP1解析阶段就把每个block的原始PDF页码（PyMuPDF内部0-indexed，输出时+1
转成人类习惯的页码）记录下来，一路带着传到parent、child、检索结果、最终答案。

**为什么不能后补**：页码信息一旦丢失，**无法从纯文本反推**——文本本身不包含"我在
第几页"这个元信息，除非重新解析原始PDF并重新做一遍位置匹配（而且切分、清洗等操作
会进一步破坏这种可逆性）。这是全项目唯一"后补代价极大"的字段。

**这条约束在实践中最容易被破坏的地方**：dev模式只处理前150页时，**绝不能因为只
处理了150页就把页码从1重新编号**——必须保持PDF原始页码。如果重新编号，STEP6切到
全量576页时，`eval/golden_qa.jsonl`里所有`gold_pages`会全部错位（因为dev编号体系
和full编号体系不是同一套），而且这个错误在dev模式下**测不出来**（因为dev自己内部
是自洽的），只有切到full才会暴露，届时已经很难排查。

## 7. 为什么检索链路手写而非用框架编排

**问题**：LlamaIndex这类框架自带`QueryEngine`/检索链编排能力，为什么不直接用？

**方案**：只用LlamaIndex的`SentenceSplitter`做纯文本切分，向量检索、BM25、融合、
重排、small-to-big全部手写。

**两个具体理由**：
1. **需要检索的中间结果**——`eval/harness.py`要机械地读取每个候选的`page_no`去和
   `gold_pages`比对计算Recall@5/@20/MRR。高层框架的Query Engine通常把检索过程封装
   成一个黑盒，只返回最终答案，拿不到"每一步召回了什么、排第几"这种中间状态。
2. **消融实验需要单变量控制**——四个开关（`use_bm25`/`use_rerank`/`use_small_to_big`）
   要能任意组合、单独开关，还要保证"改一个开关只改这一个变量"。高层框架的pipeline
   通常是预设好的组合套路，不容易拆解成这种细粒度的、可自由排列组合的开关。

**代价**：开发工作量明显更大——很多框架帮你处理好的工程细节要自己重新实现，比如
模块级单例（避免每次查询重新建连接）、`reset_*()`函数（应对dev/full切换）、
"配置指纹"缓存机制。这个项目里也确实因为手写而踩到过真实bug（BM25融合后候选数
未裁剪导致重排开销翻倍），这是手写的直接代价——框架可能已经把这类边界情况处理好了，
自己写就要自己发现、自己修。换来的好处是：每一行检索逻辑都能在面试里讲清楚原理，
这也是这个项目的立项目的之一。

## 8. 为什么 embedding 用 API 而非本地模型

**问题**：`bge-m3`模型是开源的，为什么不在本地跑？

**方案**：embedding走API（硅基流动提供的`BAAI/bge-m3`），reranker（`BAAI/bge-reranker-v2-m3`）
反而选择本地部署。**这是两种不同的选型逻辑，不是同一个偷懒决定。**

**embedding选API的理由**：本地跑embedding模型需要下载模型权重、占用内存/显存、
维护本地推理环境，个人一周项目里这些工程时间不如省下来花在检索/融合/生成这些真正
体现RAG理解深度的部分。而且embedding的调用模式是"每个query或document调一次、
输入较短"，API按量计费在这个量级下很便宜（205个child建索引全量实测约39500个
token），延迟也可接受（批量调用，非阻塞主流程）。

**reranker反而选本地的理由**：Cross-Encoder重排的每次调用都要把候选的**完整原文**
和query一起送进模型（不是像embedding那样只处理一段独立文本），而且一次查询要重排
多个候选（本项目实测20个）——如果也走API，相当于每次查询要发20次包含长文本的请求，
延迟和成本都会明显更高。本地部署虽然要多花一次性的下载/加载时间成本（实测首次加载
约6.5~6.8秒，之后常驻内存），但换来的是每次重排调用本身很快（20个候选约2.3秒，
且不产生额外API费用）。

**这条决策本身要表达的核心逻辑**：不是"能省事就都用API"或"能控制就都本地部署"这种
一刀切的原则，而是**根据每个组件的调用模式（调用频率、单次输入大小、延迟敏感度）
分别判断哪种部署方式更划算**——这个判断过程本身就是可以在面试里展开讲的工程判断力。

## 9. 为什么采用 dev/full 双数据集开发流程

**问题**：为什么不直接拿全量576页从头用到尾？

**方案**：dev模式（前150页，独立集合`askingdoc_dev`）用于开发期快速迭代，
STEP6切到full模式（全量576页，正式集合`askingdoc`）产出交付用的正式数据，
两者共用同一份代码，仅由`config.dev.enabled`一个开关切换。

**具体收益**：STEP2切分参数调整、metadata字段调试等阶段大概率要重建索引2-3次。
实测全量576页的ingest三步（解析→切分→建索引）耗时数分钟级别，而dev版150页的
建索引这一步（185个新child全量embedding）实测只要**3.8秒**——每次省下的时间
累积起来，也让"改切分参数就重新跑一次看效果"这种试错行为变得心理负担很低，
更敢于放心调整参数。

**代价**：需要设计并维护`{suffix}`隔离机制（所有路径和collection name都要经过
这一层间接），需要两份独立的索引构建（dev一份、full一份），存储空间和一次性的
构建时间是双倍的。这个代价在个人项目单机开发场景下完全可以接受。

**面试角度**：这个流程本身对应了实际工程里很常见的"用采样数据开发pipeline、
全量数据跑生产"模式，能说明有考虑开发效率和数据规模的工程习惯，不只是"跑得动"
这一个维度。

## 10. rank_bm25 的实现特点与规模边界

**问题**：这个项目用的`rank_bm25`这个Python库，内部是怎么实现的，能撑多大规模？

**方案/事实**：`rank_bm25`是一个轻量的纯Python参考实现，**不是**生产级搜索引擎
（如Elasticsearch/Lucene）用的那种倒排索引结构。读过它的`BM25Okapi.get_scores()`
源码可以确认：对query里的**每一个词**，它都会构造一个长度等于**全部文档数**的
numpy数组，遍历`self.doc_freqs`（每篇文档的词频字典列表）查这个词在**每一篇**
文档里出现了几次——也就是说，每次查询都是对整个语料库的一次**线性扫描**
（复杂度 O(query词数 × 语料文档总数)），不是"只碰含有该词的文档、跳过其余"的
倒排索引查法。

**索引本身存的是什么**：项目实测过`BM25Okapi`对象内部的实际结构——`doc_freqs`
（每篇文档的词频统计字典的列表）、`idf`（全局的词→稀有度字典，只有一份）、
`doc_len`/`avgdl`（文档长度和语料平均长度，用于长度归一化）、`k1`/`b`两个调参
常数。这些都是普通的Python list/dict，没有任何树/图结构（这点跟向量索引的HNSW
图结构不同）。项目里选择只把**分词结果**pickle存盘、不存整个`BM25Okapi`对象，
是因为重建这些统计量很快（205篇文档几毫秒级别），而pickle一整个类实例在库版本
升级时容易因为内部属性变化而反序列化失败。

**规模边界（诚实的局限说明）**：在这个项目的量级（几百到几千条child文档）下，
线性扫描完全不是问题，实测查询延迟可以忽略不计。但如果语料规模涨到**十万级文档**，
每次查询都要扫一遍十万篇文档的词频表，延迟会线性增长到不可接受——这时候就需要
换成真正的倒排索引实现（词→包含它的文档ID列表），查询时只碰含有查询词的那一小撮
文档，跳过不相关的绝大多数。这不是`rank_bm25`这个库能优化解决的，是它作为轻量
参考实现的设计取舍——本项目选它是因为规模合适、部署简单（纯Python无需额外服务），
